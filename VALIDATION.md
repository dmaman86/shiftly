# Validation

## Purpose and Review Status

This document answers: **what evidence supports Shiftly's payroll calculations, and what does that evidence not guarantee?**

The primary target is the framework-independent payroll domain. UI and browser tests support application reliability; when expected results come from independent real-world references, their calculation assertions also contribute business-result validation for those scenarios.

**Repository review: 2026-10-04.** This update inspected source code, test assertions, package scripts and CI configuration. It did not run tests, collect coverage, execute a build, compare a payslip, or independently reverify external rate circulars.

The distinction used throughout is:

- **Existing evidence:** a concrete test or configured check is present.
- **Known limitation:** implemented behavior differs from a desired validation guarantee, or authoritative evidence is incomplete.
- **Planned validation:** additional evidence or tooling is proposed but not implemented.

A test's presence is not a fresh passing result, and a passing implementation test is not independent confirmation of the business rule encoded in its expected values.

The project owner clarified on 2026-10-04 that `e2e/fixtures/*.result.json` was initially generated by Shiftly and subsequently corrected against actual payslips. The current files contain real-world reference results according to that confirmation; they were not created entirely independently of the system. Their external validation source is actual payslips, while their initial structure and values came from Shiftly. This review did not inspect the original payslips or a field-by-field reconciliation record. The corrected expected results provide real-world comparison evidence for the scenarios exercised by the linked tests, rather than merely preserving unchecked implementation outputs.

### Basis for the Current Marks

The marks reflect the reviewed assertions and limitations in the evidence inventory below, not a fresh test execution or an exhaustive certification of an employment contract. A unit validation mark is limited to the example-based behavior documented there.

- Regular, addition, special-time, cross-midnight, absence and aggregation unit marks are backed by assertions of calculated values or classified intervals, not just module availability.
- `SpecialPartial` retains the original matrix label; its evidence exercises the current `SpecialPartialStart` domain type.
- Boundary marks remain partial: representative transitions are exercised, but complete before/at/after coverage has not been established for each rule. In particular, the addition suite checks below and above evening qualification without proving every exact-threshold case.
- Holiday tests exercise supplied holiday metadata and day types; they do not independently verify the external calendar. Cross-month tests exercise next-month continuation and a year-boundary shift, not persisted allocation across two reports.
- DST unit/boundary validation is partial. The regression mark is specifically supported by `pays wall-clock hours on the autumn daylight-saving transition night` in the [day-from-shifts suite](packages/domain/tests/calculator/day-from-shifts.calculator.test.ts).

- Other regression cells remain undocumented: an edge-case test alone does not establish its connection to a confirmed defect. Property means generated property-based testing; ordinary example assertions are not marked as property coverage.
- Property and mutation cells remain empty for the reasons in **Validation Methods Not Yet Established**. Empty cells mean evidence has not been documented, not that every related test is absent.
- Real-world marks use the owner-confirmed payslip-corrected result files and the [four-month integration suite](apps/web/src/test/integration/work-table-month-fixtures.test.ts), which compares daily/monthly breakdowns and salaries. All four fixtures contain nonzero regular, overtime, evening, night and special results; October 2021 and March 2022 include sick/vacation entries. ## Calculation Contract Relevant to Validation

Detailed calculation explanations belong in the [English reference](docs/reference/README.md), [Hebrew reference](docs/reference/README_HE.md) and the application [calculation-rules page](apps/web/src/pages/CalculationRulesPage.tsx). The following constraints determine how validation cases must be interpreted.

### Configurable Hours, Not a Universal 6.67 Constant

The application's [default monthly configuration](apps/web/src/store/globalStore.ts) sets `standardHours=6.67`. The [base-hours classifier](packages/domain/src/calculator/regular/base-hours.classifier.ts) receives that threshold as input, followed by up to two hours at 125% and the remainder at 150%.

Absence credits also use supplied durations; the [fixed-segment calculator](packages/domain/src/calculator/fixed-segment.calculator.ts) does not hardcode 6.67 hours. Test both the default and a non-default configuration, rather than treating a single threshold as a universal contract rule.

### Additions and Special Time Are Separate

The current [addition policy](packages/domain/src/calculator/additions/addition.classifier.ts) defaults to evening +20% for qualifying regular time in 14:00–22:00, with at least 180 qualifying minutes per applicable calendar day, and night +50% in 22:00–06:00. Special intervals are excluded from this addition classifier.

The [timeline pay calculator](packages/domain/src/calculator/timeline-shift-pay.calculator.ts) composes base, additions and special classifications. Tests must distinguish mutually exclusive base categories from additive representations; overlapping supplement representations are not automatically duplicated worked time.

The current enum uses `SpecialPartialStart`, not `SpecialPartial`. Special-day transitions and carry-through to 06:00 must be checked with explicit day metadata and calendar expectations, not inferred from weekday names alone.

### Wall-Clock Duration and DST

Payroll duration uses local wall-clock minutes, not simply elapsed UTC milliseconds. The [shift service](packages/domain/src/services/shift.service.ts) normalizes cross-day minutes using 1,440 minutes per local day.

The regression `pays wall-clock hours on the autumn daylight-saving transition night` in the [day-from-shifts suite](packages/domain/tests/calculator/day-from-shifts.calculator.test.ts) makes this contract explicit. [Date conversion](packages/domain/src/services/date.service.ts), repeated/nonexistent local times and seasonal special-start offsets are separate concerns; one autumn example does not establish complete DST support.

### Historical Recalculation Is Not a Frozen Payroll Snapshot

`AdditionPolicy` can select additions by calendar date, and allowance calculators have effective-period tables. Neither mechanism versions all payroll rules, defaults, calendar inputs or rounding behavior.

The profile recalculates saved months with the current domain engine, as documented in [profile analytics](docs/profile-analytics.md). Do not claim historical totals remain immutable after all future engine changes. A complete historical-rules guarantee requires an explicit supported-period policy and independently reviewed fixtures.

## Known Limitations and Implementation Gaps

### Historical Rate Evidence Versus Implemented Fallbacks

The historical source reference below must not be confused with the implementation's supported, authoritative periods.

- [Duty per diem](packages/domain/src/calculator/perdiem/timeline-per-diem.calculator.ts) assigns provisional starts at November 2015 and January 2021, and returns zero before its timeline. The source reference does not establish those exact effective dates.
- [Meal allowance](packages/domain/src/calculator/mealallowance/timeline-meal-allowance.calculator.ts) extends a provisional small/large baseline back to January 2000 and returns zero before its timeline. The retained reference does not establish meal amounts before June 2017.
- The per-diem calculator derives tier amounts from a base rate and points. Tests must not treat that arithmetic as independent confirmation of every separately listed official category amount.
- Meal allowance currently models small/large rates and its own eligibility conditions. The reference circulars list an additional category without a meal agreement; the reference table does not imply that every category is implemented.
- Existing rate tests intentionally encode provisional baselines and zero fallbacks. Their passing would confirm that behavior, not eliminate the missing historical evidence.

The desired validation behavior is to distinguish a legitimate zero entitlement from an unknown historical rate. The current return shapes do not provide that distinction. Changing this behavior requires a separately reviewed calculation/API change; this documentation update does not alter it.

### Boundary, Input and Reporting Gaps

- Cross-month classification examples do not by themselves prove how persisted shifts are attributed across two monthly reports. Establish the intended ownership before asserting segment-based monthly allocation.
- The generic fixed-segment calculator preserves its numeric input, including negative values in its tests. Non-negative credited durations require an explicit valid-input contract and validation at the responsible boundary; do not assert that every calculator enforces it.
- Holiday calendars, employer-specific exceptions and civil-time conversion are inputs to correctness, not facts guaranteed by a classification test.
- Currency precision, rounding order and external payroll adjustments need explicit comparison rules. JavaScript arithmetic is not evidence of an exact-agorot monetary model.

### Scope of Payroll Comparisons

Shiftly does not reproduce all employer payroll components. Reimbursements, deductions, tax, pension and manual corrections may be outside the engine.

Compare equivalent hour-based earning components, not Shiftly's total against net salary. A difference must be classified as a calculation defect, missing rule, unsupported component, input discrepancy or documented rounding difference.

A single matching month is useful evidence but does not prove correctness for all periods or inputs.

### Rules-version and boundary validation

The following are validation targets, not a description of guarantees already provided by the implementation:

1. **Independent histories:** updating meal allowance must not change duty per diem or imply a matching effective date.
2. **Effective-date selection:** select the rate using the domain-defined entitlement date in `Asia/Jerusalem`. For cross-midnight entitlements, explicitly specify whether the governing rules use a start date, another attribution date, or separate entitlements; do not automatically prorate a fixed allowance by shift segments.
3. **Known boundaries:** verify meal allowance immediately before and on `2017-06-01` and `2021-07-01`; verify both families on `2022-09-30` / `2022-10-01` and `2024-08-31` / `2024-09-01`, with an additional case after each update. The pre-2017 meal case must report unresolved historical data, not assert an invented amount.
4. **Retroactive publication:** September 2024 entitlements use the September 1 rates even though guidance was issued September 18; October 2022 meal entitlements use the October 1 rates despite the 2023 circular reference.
5. **All categories:** assert each value in the supported rate triplets, not only the first category. Check qualification just below, exactly at, and above applicable thresholds under the governing eligibility rules.
6. **Missing evidence:** unresolved meal amounts and the uncertain older duty transition produce an explicit unsupported/unresolved result or require a documented, scoped override. Never silently substitute the earliest known, latest, or zero rate.
7. **Historical stability:** introducing a later rate must leave previously validated periods unchanged. Use exact currency representation, such as integer agorot, and document any rounding separately.
8. **Traceability:** each historical fixture should record its rate family, category, entitlement date, expected amount, rules version, source circular, and evidence status. A user-observed amount is not interchangeable with an officially established effective date.

The two remaining historical gaps are the exact older duty-per-diem transition and meal allowance amounts before `2017-06-01`. The retrospective discrepancy in 2024-3-15 is a separate source-quality issue. No complete, officially validated rate dataset from 2015 is claimed.

This section records retained reference evidence and required validation cases. The evidence matrix above identifies existing implementation tests separately from unresolved historical-source questions. Open-ended 2024 rows must be reviewed when additional official guidance is identified; this update does not assert that no later 2025/2026 circular exists.


## Validation Plan

The priorities below add missing evidence before introducing new tools or a complete rules-version architecture.

### 1. Close High-Risk Example Gaps

- For each supported rule, exercise a typical input plus immediately below, exactly at and immediately above relevant boundaries: 06:00, 14:00, seasonal 17:00/18:00, 22:00, midnight, overtime and qualification thresholds.
- Include non-default standard hours, special-day interactions and per-calendar-day addition qualification.
- Define and test persisted cross-month ownership, both DST transitions and repeated/nonexistent local-time handling.
- Confirm historical effective dates, all supported rate categories and rounding against authoritative evidence. Preserve unresolved cases explicitly.
- Convert each confirmed defect into a permanent regression with the original scenario, expected result and responsible test. Do not invent previous bug behavior from a test name.

### 2. Specify Invariants on Valid Inputs

Candidate properties are:

- Base timeline slices conserve normalized wall-clock duration and do not overlap.
- Valid normalized slices have non-negative duration and ordered endpoints.
- Recalculation with identical inputs and the same engine/policy yields the same result.
- Aggregation is order-independent only for rules whose semantics do not depend on chronological accumulation.
- Artificial splitting preserves results only within the same semantic aggregation scope. Shift-level overtime, per-day qualification and fixed allowances can make independent recalculation of split pieces inequivalent.
- Shabbat credit respects available credit, eligible deficits and chronological allocation.

Apply numerical tolerances where the implementation uses floating-point hours. Define which base quantities are conserved; do not sum base hours and overlapping supplement hours as if both were worked time.

Start with deterministic examples or bounded enumerations for these invariants. Consider a property-testing library only when reproducible generated cases and shrinking provide concrete value. Record seeds and minimized failures if adopted.

### 3. Evaluate Targeted Mutation Testing

Mutation testing is planned, not enabled. If assertion strength remains uncertain after boundary review, trial a small critical scope: threshold comparisons, percentages, special-start offsets and inclusion/exclusion branches.

Document the tool configuration, tested commit, scope, score and surviving-mutant analysis before making mutation-based claims. A high aggregate score must not hide surviving defects in payroll-critical logic.

### 4. Extend and Document Real-World Comparisons

The payslip-corrected result fixtures already provide comparison records for four months. Preserve the externally reconciled values when maintaining them: do not overwrite them with freshly generated Shiftly outputs to make a failing comparison pass. Generation can bootstrap a fixture, but its results must be checked and corrected against the external reference before they count as real-world evidence. Extend scenario coverage and document both generation history and reconciliation provenance without publishing sensitive original records.

Each comparison should identify:

- Period, engine revision and applicable policy/configuration.
- Reference source and whether it is authoritative, manually checked or provisional.

- Actual values, rounding/tolerance and explained differences.
- Unsupported components and unresolved discrepancies.

Do not publish identifying payroll data or use fixtures generated by the same implementation as an independent oracle.

### Acceptance and Evidence Maintenance

For a defined supported scope, confidence increases when reviewed rule fixtures, boundary cases, regressions and relevant invariants are reproducible in CI, with remaining discrepancies documented. Property tests, mutation testing and real-world comparisons contribute additional evidence when available; their absence must remain visible rather than being implied by passing unit tests.

For every new claim, link the responsible test and, when claiming execution success, the specific CI run or report and commit. Keep authoritative-rule evidence separate from implementation expectations. Do not label all historical payroll rules validated while provisional rates or unsupported periods remain.
